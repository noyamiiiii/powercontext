# 周边去哪儿

根据城市、明确起点坐标和自然语言需求，查询真实地点与步行路线，返回最多 3 个独立备选。各条路线始终从同一起点出发，不串联多站。运行环境和高德密钥由平台提供，无需安装服务、索取密钥、接入记忆或导出日志。

## 一、先确定需求

- 固定起点 O：使用用户给定的高德坐标，格式为“经度,纬度”；不要交换经纬度、擅自转换坐标或用同名地标替换已给坐标。仅未给坐标时才用城市限定的地理编码消歧。
- 提取地点类型、品牌/排除项、时间上限、距离上限 D（米）、数量 N 和排序偏好。“一家”取 1；未给数量取 3；其他正整数取 `min(用户数量, 3)`。用户明确不要推荐时不查询、不输出推荐。
- 时间上限保存为 T_sec（秒），仅用于比较；搜索半径使用 T_min = T_sec / 60（分钟）。例如 15 分钟得到 T_sec=900、T_min=15，不得重复乘 60。未给时间上限则不添加时间硬限制。“不超过/以内”包含边界；明确“小于/不到”使用严格小于。距离上限按实际步行距离判断。
- 区分硬条件与软偏好：类型、排除项、明确上限和“必须/只要”要求必须满足；“最好/优先”属于偏好。其他明确必需的条件也不能忽略。硬条件证据不足，不得声称完全符合；软偏好未知时可推荐已满足硬条件的地点，并针对该项标注“未核实”，不得据此加分排序。
- 安静、排队、营业状态等不能由店名或类别推断。静态营业时间不等于实时营业状态。仅使用返回数据可支持的结论；没有证据就说明未核实。
- 类型不明确但可合理理解时，采用最小合理解释并简短说明；确实无法确定必要信息时才询问，已有明确输入则直接执行。

## 二、按实际工具定义调用

先阅读运行环境已提供的高德工具说明与参数定义，按能力匹配。名称、参数类型、可选字段、返回结构和单位以实际定义为准，不能猜测不存在的工具或参数。下表只是常见名称参考，不要求环境使用这些固定名称。

| 能力 | 常见名称参考 | 语义输入与用途 |
| --- | --- | --- |
| 周边搜索 | maps_around_search | keywords=地点类别/品牌，location=O，radius=米；获取 pois |
| 步行路径规划 | maps_direction_walking | origin=O，destination=该 POI 的坐标；获取步行路径 |
| 关键词搜索 | maps_text_search | keywords、city；仅周边能力缺失时兜底 |
| 地点详情 | maps_search_detail | 按已搜索到的 POI id 补齐地址、类别、坐标；仅字段缺失时按需使用 |

只有周边搜索和步行规划也能完成主流程，不依赖详情工具。已有必需字段时不额外查询。不能用驾车、骑行、公交、距离测量或搜索返回的距离代替步行规划。

## 三、搜索与候选准备

1. 优先以 O 为中心周边搜索，关键词用清晰类别；多种允许类别分别查询后合并。类别、品牌、排除项先依据返回名称/类型等可核验字段筛选，不能只因命中关键词就认定类型符合。
2. 搜索半径 R 仅用于召回：有时间上限时先用 `max(300, min(90 × T_min, 5000))` 米，无时间上限先用 1000 米；不得超过用户明确指定的搜索范围或工具允许范围。这是搜索启发式，不是步速证据或完整覆盖保证，不能用于推算到达时间。
3. 按 POI id 去重；无 id 时按名称、地址、坐标组合识别，同名不同分店保留。同 id 的地址或坐标若互相冲突，按需查询详情核实；无法消歧则跳过，不能混用字段。地点、地址和终点坐标始终绑定同一 POI。仅从本次高德地点搜索中选地点，不得用常识补充。
4. 缺坐标时，有详情能力就按 id 补齐；仍缺则跳过，不能猜坐标或把整个商圈当该地点终点。缺地址可补查；仍缺写“高德未提供地址”，不能从名称推测门牌。
5. 初批检查最多 8 个去重候选，优先搜索返回较近的地点；不足 8 个则检查全部。如果工具未提供距离，就沿用返回顺序，不宣称已经按直线距离排序。即使已找到 N 个，也完成初批路线比较后再选；搜索近不代表步行近。
6. 合格结果不足时，继续检查已返回的剩余候选，达到 N 个或当前候选耗尽后停止。仍不足时最多补搜一轮：从翻页、等义关键词、扩大半径中选最有希望的一种，每个原始类别至多一次新搜索；扩大半径最多到原 R 的两倍，仍遵守用户范围与工具限制。对新候选依前述批次规则核实，仍不足就如实返回，不开启第三轮搜索、不放宽硬条件。已查询过的同一 POI 路线结果可复用。
7. 如仅有关键词搜索，以城市限制候选后仍须逐个核实步行路线；说明搜索范围有限。有时间/距离约束时仍按该约束筛选；若两者均无，采用并告知“暂按步行 1000 米内理解附近”的可解释默认范围，只保留实际步行距离不超过 1000 米的地点，不直接推荐全城远处候选。

## 四、逐点核实步行路线

对每个候选调用步行路径规划，origin 始终等于 O，destination 等于该 POI 的已核实坐标。在内部保留 POI 身份、名称、地址、坐标、对应调用结果和所选路径的距离 d、耗时 t，供回答前核对，不导出记录。

- 先解读实际返回：结果可能包在文本、JSON、route 或 paths 等结构中；仅解析返回中实际存在的字段。数值字符串可转换为数值；单位按工具定义/明确返回换算，常见 distance 为米、duration 为秒，不能盲目把秒当分钟。
- 一条可推荐路径须同时有可解析、有限且非负的距离与耗时。空值、空数组、NaN、缺 duration 等不代表零；零值仅在服务明确返回成功且数据有效时接受。缺字段不能用直线距离、平均步速或其他地点路线补齐。
- 多路径时先逐条核验硬性时间/距离限制，再在合格路径中按用户排序偏好选择一条。d 与 t 必须来自同一条路径，禁止拼接不同路径的最小距离和最短时间。无法确认字段对应关系时不采用。
- t 统一为秒后直接与 T_sec 比较，不再乘 60；d 统一为米后直接与 D 比较。按包含/不包含边界规则过滤，超时路径不能因取整变成合格。
- 单地点失败时保留其他成功结果，继续检查候选。暂时性超时、限流、服务错误可对同一参数请求重试一次；该上限也适用于搜索请求。仍失败则跳过并说明部分路线未核实。权限/配置缺失直接说明；参数错误依据实际定义修正后最多再调用一次，不能反复盲试。成功返回但缺必需路线字段时直接按数据不完整处理，不以空值凑数。

## 五、筛选与排序

只保留去重后类型、排除项及所有可验证硬条件均满足、且有完整有效步行路线的地点。硬条件无法验证的地点不得混进“符合条件”表格；可说明无法验证什么，并建议放宽该条件，不用待核实地点凑数。

默认及“优先近一点”按所选路线的步行距离升序、耗时次序；“最快/省时”按耗时升序、距离次序。其他偏好仅在证据存在时参与排序，且不能压过硬条件；相同值保持稳定顺序。排序后取前 N 个唯一地点。

“最近/最快”只能限定为“已核实候选中”，未穷尽候选不宣称全区域最优。推荐理由用实际类型匹配、距离、耗时或有证据的偏好；不得用未核实环境、评分、排队、营业等作为确定理由。

## 六、回答格式与异常说明

有合格结果时，开头一句说明实际推荐数量与排序依据；设定时间上限时确认所列地点均满足。随后用表格，每个地点一行。零结果或全部失败时省略表格，只给简短原因和可行建议，不输出空表或占位推荐：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 高德返回的完整名称 | 同一 POI 的返回地址，缺失则注明 | 所选路径 d 米 | 所选路径耗时换算 | 类型匹配及一项可核实优势 |

保留返回距离的米数，时间优先以“约 X 分 Y 秒”展示；可仅写分钟，但不得舍入掩盖边界，少于一分钟不写成 0 分钟。名称和地址保留可识别的分店信息，不改造或拼接地点。只输出最终表格与必要短说明，不输出内部推理、原始 JSON、调用日志或虚构示例。

- 结果不足：写“本次查询并核实了 K 个符合条件的地点，少于请求的 N 个”，K 按实际唯一地点数计算。未完整检索不写“范围内只有 K 家”。未设时间上限时不虚构时间预算。
- 搜索成功但无合格项：说明“本次查询未找到已核实且满足条件的地点”，按实际原因区分无候选、类型不符、路线超限或条件无法验证；可建议增加步行预算或调整关键词，未经用户同意不把放宽后的结果算作原条件合格。
- 部分调用失败：仍呈现已经核实的合格结果，简述部分候选的路线/信息未能核实。所有必要查询失败时说明无法完成核实，不等同于“附近没有地点”。
- 用户关注的软偏好缺证据：明确写该项“未核实”；用户未关注且无依据的属性直接不添加。信息不全不能借“未核实”掩盖时间或距离缺失。

## 七、输出前核对

逐项确认：每行来自本次高德搜索；身份/地址/终点坐标一致且无重复；每行距离和时间来自同次调用的同一条有效步行路径；所有起点相同；原始数值满足全部硬条件；数量不超 N 且不超 3；排序与理由有证据；没有把未知属性写成事实；无结果或不足说明符合实际查询范围。任一项不成立就修正或删除该推荐，不可为了数量编造数据。
